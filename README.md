## 1. 과제와 데이터

**입력** 사진 1장 + 질문 + 보기 4개 (a~d) → **출력** 정답 소문자 한 글자.
간판 · 가격표 · 전화번호 · 안내문처럼 **사진 속 한국어 글자를 정확히 읽어야** 풀 수 있는 문제가 대부분입니다.

| 데이터 | 문항 수 | 정답 |
|---|---|---|
| train | 6,714 | 1개 |
| dev | 2,683 | 5명 투표 (`answer1` ~ `answer5`) → 다수결, 1위 동률 465문항 제외 → **2,216문항** 평가 |
| test | 6,714 | 비공개 (캐글 채점) |

**제약** 외부 API 사용 금지 → 공개 모델을 직접 파인튜닝. 자원은 RTX 5060 Ti 16GB PC 5대(3일) + Google Colab(A100 40GB).

**사진 크기** test 사진의 약 80%가 **720 × 960 · 960 × 720** (0.69 메가픽셀). 해상도 전략을 정하는 데 중요한 사실이었습니다 ([6-6](#6-6-오답-분석)).

### dev 정답 노이즈 발견
| dev 투표 구조 (평가 대상 2,216문항) | 문항 수 |
|---|---|
| 1위 3표 · 2위 2표 | 1,002 |
| 1위 3표 · 2위 1표 | 1,007 |
| 1위 2표 | 190 |

한 사람의 답이 다수결과 같은 비율이 평균 61%에 불과하고, 만장일치는 0.8%입니다. 우리 모델의 dev 정확도(0.70)와 리더보드(0.96)를 맞춰 보면 **dev 다수결 정답의 약 27%가 실제와 다른 노이즈**로 추정됩니다. 그래서 **dev 는 모델 간 상대 비교용으로만 쓰고, 최종 판단은 리더보드로** 했습니다.

## 3. 실험 설계 원칙

1. **한 번에 변수 하나** — 기준 실행(A)을 두고 팀원마다 한 변수만 바꿔 비교 (B 데이터량 · C/D 해상도 · D LoRA rank · 시드).
2. **흔들림 기준 1%p** — 같은 설정에서 시드만 바꾸면 dev 0.3%p 차이. 보수적으로 **1%p 이내 차이는 우연**으로 판정.
3. **판단은 리더보드** — dev 노이즈 때문에 dev 순위와 리더보드 순위가 여러 번 뒤집힘 (예: dev 0.6200 → 0.9121, dev 0.6273 → 0.8999).
4. **검증을 코드에 박아두기** — 모든 노트북에 아래 확인 셀을 넣어, 잘못된 설정으로 GPU 시간을 쓰기 전에 멈추게 함.
   - 라벨 마스킹 검증: loss 대상이 정답 한 글자 + 종료 토큰인지 디코딩해서 확인
   - 제로샷 확인: 학습 전 예측이 한 글자에 몰리지 않는지
   - 속도 가드: 학습 40스텝째 샘플당 시간이 기준을 넘으면 자동 중단
   - 재현 확인: 저장된 모델을 다시 불러와 추론할 때 기존 답과 93~95% 이상 같아야 진행
   - 시간 · 예산 계산: 파일럿이 실측 속도로 본 학습 규모를 자동 추천
5. **중간 산출물은 전부 드라이브에 저장** — epoch 마다 어댑터, test 는 1,000문항마다, TTA 는 조합마다. 세션이 끊겨도 이어서 실행 (`RESUME_TEST_ONLY`).

## 4. 데이터 가공

| 구분 | 원본 | 가공 | 이유 |
|---|---|---|---|
| **이미지** | 크기가 제각각인 사진 | 총 픽셀 수를 `IMAGE_SIZE²` 예산에 맞춰 비율 유지 리사이즈, 가로 · 세로를 32의 배수로 (바이큐빅). processor 의 `min_pixels = max_pixels = IMAGE_SIZE²` 로 고정 | 이미지 토큰 수를 고정해 학습 · 추론 일치. 32 = 패치 16 × 병합 2 |
| **텍스트** | 질문 + 보기 4개 | 시스템 지시문 + `질문\n(a) …\n(b) …\n(c) …\n(d) …\n\n정답을 반드시 a, b, c, d 중 하나의 소문자 한 글자로만 출력하세요.` | 형식을 고정해 한 글자 출력을 안정화 |
| **정답 (학습)** | a/b/c/d | 채팅 템플릿으로 `프롬프트 + 정답 + <|im_end|>` 구성 후, **프롬프트 부분은 라벨 -100 으로 마스킹** → 정답 글자 · 종료 토큰(3토큰)에만 loss | 원래 코드는 316토큰 전체에 loss 가 걸려 정답 신호가 희석됨 |
| **정답 (평가)** | dev 5명 투표 | 다수결, 1위 동률 제외 (2,216문항). 시드 고정 셔플 후 앞에서 N 개 → 실행 간 **같은 문항으로 비교 가능** | 투표가 갈린 문항은 정답을 신뢰할 수 없음 |
| **답 추출** | 문장 생성 후 파싱 | 마지막 위치 로짓에서 `a/b/c/d` 네 토큰만 비교 (softmax 확률 저장) | 형식 오류 0, 확률을 앙상블에 그대로 사용 |
| **증강** (선택) | — | 밝기 · 대비 · 채도 ±20%, ±3° 회전, 가장자리 5% 크롭, 가끔 약한 블러. **뒤집기 · 큰 회전 · 강한 블러 금지** (글자가 망가짐). 학습에만 적용 | 1 epoch 에선 −1.1%p, 전량 2 epoch 에선 본선 최고점 → 조건부 |

## 5. 모델 선택

이미지와 텍스트를 함께 이해하는 **VLM** 이 필요했고, 16GB GPU 에서 학습 가능해야 했습니다.

| 후보 | 결과 | 판단 |
|---|---|---|
| Qwen2.5-VL-3B | 베이스라인 모델. 640px 에서 0.9163 | 가볍지만 글자 인식이 약함. 대신 **다른 세대라 앙상블 다양성에 크게 기여** |
| **Qwen3-VL-8B** | **주력 모델** | 글자 인식(OCR)이 강함 · **해상도를 자유롭게 조절 가능(동적 해상도)** · 4bit + LoRA 로 16GB 에 탑재 · 비전 인코더까지 LoRA 학습 가능 |
| Qwen3-VL-32B | A100 에서 4bit 로 학습. 단일 0.95710 | 같은 가족이라 파이프라인 그대로 사용. 단일 개선폭은 작았으나 앙상블 재료로 사용 |
| Qwen3.5-9B | 전량 1 epoch 학습 후 **dev 0.454** (학습 실패) | 학습 문제는 72%, 새 문제는 42% → 이미지를 보지 못하고 문장만 외운 패턴. 원인 미해결로 제외 ([10](#10-트러블슈팅-기록)) |

**Qwen3-VL-8B 의 단점과 대응**
- 4bit 압축 손실 → 코랩 A100 에선 bf16 으로도 학습
- 16GB 에서 1024px 이상은 메모리 초과 (13배 느려짐) → 고해상도 학습은 A100 에서
- 첫 보기(a)를 고르는 위치 편향 → 로짓 채점 + 보기 순서 이동 TTA

| 6개 모델 전원 동의 | 5,963문항 (88.8%) |

| 사진 크기와의 관계 | 대부분 960px 원본이라 크기별 차이 1%p 이내 → 더 높은 해상도는 해법 아님 |
| 불확실 사진 직접 확인 | 가려진 글자 · 상호명이 둘 · '모두 정답' 보기 · **한 글자만 바꾼 함정 보기** |

결정적 사례 `test_2012`: 6개 중 **5개 모델이 b** 를 골랐는데, 32B(비중 40%) 하나의 확신 때문에 최종 답이 d 로 뒤집힘.
→ **불확실 문항에서 한 모델의 과신을 제거**하는 보정을 시험.

| 보정 | 리더보드 |
|---|---|
| m2 (32B 40% 가중) | 0.96455 |
| 불확실 문항만 6개 모델 다수결 | 0.96514 |
| 불확실 문항만 **같은 비중 확률 평균** | **0.96574** |
| **전체를 같은 비중 확률 평균 (`eq_all`)** | **0.96574** |
| 투표 인원 11명 (약한 단일 모델 포함) | 0.96336 |
| 같은 비중 로그 확률 평균 | 0.96395 |

→ 조건 분기 없이 **강한 모델 6개를 같은 비중으로 평균**하는 가장 단순한 방법이 최고점. 공개 점수에 맞춘 미세 조정이 아니라 원리적인 방법이라 최종 제출로 선택.

## 11. 한계와 배운 점

**배운 점**
1. **과제의 병목부터 찾기** — 글자 읽기 과제에선 모델 크기보다 해상도가 먼저였다 (8B · 512px < 3B · 640px).
2. **노이즈 라벨은 순위 참고만** — dev 다수결의 약 27%가 노이즈. 판단은 리더보드로.
3. **학습 없이도 오른다** — TTA 로 +1.6%p. 단, 이미 원본 이상 해상도로 보는 모델에선 효과가 작다.
4. **앙상블은 체급과 다양성** — 약한 모델을 많이 섞으면 떨어지고, 체급이 비슷하면서 다르게 보는 모델(다른 해상도 · 다른 세대)을 섞으면 오른다.
5. **오답을 데이터로 보기** — 정답이 없는 test 에서도 모델 간 불일치로 오답 후보를 좁히고, 사진을 직접 보며 "한 모델의 과신"이라는 원인을 찾아 고쳤다. 막판 +0.12%p 는 분석으로 번 점수.
6. **검증을 코드에** — 마스킹 · 재현 · 속도 · 예산 확인 셀이 잘못된 설정으로 GPU 시간을 쓰는 사고를 여러 번 막았다.

**한계**
- 목표 0.97 에는 0.43%p (공개 구간 약 30문항) 부족. 남은 오답은 가려진 글자 · 이름이 둘인 상호 · 한 글자만 바꾼 함정 보기 등 사람도 헷갈리는 문항이 섞여 있다.
- 다른 팀이 사용한 Qwen3.5-9B 를 제대로 학습시키지 못했다. 경고 문서만 보고 초기에 보류했던 것, 이후 정확도 파일럿 없이 본 학습에 들어간 것이 아쉬움.
- 32B 는 dev 에서 +2.6%p 였지만 리더보드 단일은 +0.18%p 로, 추가 학습 데이터 · epoch 대비 효율이 낮았다.
- 최종 Private 0.96395 (Public 대비 −0.18%p) — [12. 회고](#12-회고--public-과-private) 참고.

## 12. 회고 — Public 과 Private

| | Public | Private |
|---|---|---|
| 점수 | 0.96574 | 0.96395 (−0.18%p) |
| 전국 순위 | 78위 | 118위 |
| 반 · 부울경 | 1위 · 5위 | 1위 · 9위 |

막판 보정 단계에서 공개 점수 차이가 **0.03 ~ 0.06%p (공개 구간 몇 문항)** 수준까지 줄어들어, 공개 점수에만 맞추는 미세 조정의 위험이 컸습니다. 그래서 최종 제출은

- 공개 최고점 중 **가장 단순하고 원리적인 방법** (`eq_all` · 조건 분기 없는 같은 비중 평균)
- 구성과 비중이 **다른 조합** (`m3_f3_32b25`) 을 보험으로
